\section{Design And Implementation}

\subsection{Game Environments}
Tic-tac-toe and Azul provide two-player game environments that place different demands on the agents. Tic-tac-toe has a small number of legal moves, deterministic outcomes and strictly alternating turns. Azul can offer many more legal moves, while random tile draws during factory refills introduce uncertainty. During a game of Azul, turns usually alternate within a round, but the same player can make the final move of one round and the first move of the next round. These differences motivate a common set of game operations and configurations that can support both games and provide a basis for adding further environments.\\

The two environments expose a common set of operations so that agents can interact with either game. Each identifies its two players and the \texttt{current\_player}, returns the legal actions for that player using \texttt{get\_legal\_actions}, and reports whether the game has ended and who, if anyone, has won. Agents can apply a move with \texttt{make\_move}, while search agents can use \texttt{clone} to explore possible moves without changing the current game. For searches that handle randomness explicitly, \texttt{apply\_deterministic\_move} performs the predictable part of a move, \texttt{chance\_node\_required} indicates whether a random event is pending, and \texttt{resolve\_chance} performs that event where applicable. The environments also provide score bounds, a readable display, equality comparison and a game identifier for supporting tasks.\\

\subsection{Minimax}

Minimax is a search-based agent that works by searching all possible game states. At the start of each decision, the player choosing a move is treated as Max and the opponent as Min. From the current game state, the agent explores each legal move and its possible successor states until the game ends. A Max win receives a favourable value, a draw receives zero, and a Min win receives an unfavourable value. These values are passed back through the tree: Max selects the highest value among its children, while Min selects the lowest. The agent then returns the move with the highest value from the current state. With tic-tac-toe, Minimax can run from the empty board in 1.16 seconds. Computing the entire game tree with Azul is estimated to take thousands of years which is why it is necessary to make changes to the pure Minimax algorithm to support Azul.

\subsubsection{Azul Compatibility (Fixed Depth Search and Chance Handling)}
As discussed in Section 4.1, Azul presents two difficulties for the full-depth Minimax agent used in tic-tac-toe: it can offer many more legal moves, and its factory refills are random. To control the cost of exploring possible moves, the fixed-depth agent searches only a specified number of moves ahead. If the game has not ended at that depth, a heuristic estimates the value of the resulting state. The Azul heuristic estimates each player’s score after resolving their current board, then compares the scores from Max’s perspective by calculating the net score difference. The graph below displays how the time taken to choose a single move increases exponentially with the search depth. \\

The random refills require a separate decision about how the search should continue. The fixed-depth agent therefore uses a configurable chance policy when a refill is needed. The round termination policy stops the search at that point and evaluates the state with the heuristic. The sampled refills policy generates a specified number of possible refills, continues the search from each resulting state, and averages their values. The graph below shows a comparison between net score and full game runtime across different number of samples. \\

Although the net score does not improve with the increase in number of samples, this is highly likely due to the search depth being 2. Using the sampled refills policy with 5 samples appears to provide a good trade-of between time and the ability to reason about the outcomes of a random refill. Running fixed-depth Minimax at a max depth of 3, with 5 sampled refills results in an average net score of 54.2 and an average full-game runtime of 78.09 seconds.

\subsubsection{Alpha-beta Pruning}
Although fixed-depth Minimax made it possible to use Minimax in Azul, searching at a greater depth remains costly since each position can have many legal moves. Alpha-beta pruning reduces the number of branches examined before making a decision. It keeps track of two bounds while searching: alpha is the highest value Max has found so far along the current path, and beta is the lowest value Min has found. These bounds are constantly updated as the tree is explored.\\

When alpha becomes greater than or equal to beta, the remaining moves at that node cannot affect the decision higher in the tree, and are hence skipped. The agent still searches to the same depth and uses the same heuristic and chance policy. The aim of this change is to reduce search work rather than change how a position is valued. At a depth of 3, Minimax with Alpha-beta pruning computes a single move in approximately 0.554 seconds compared to 37.6 seconds taken without pruning.

\subsubsection{Move Ordering}
The order in which alpha-beta search examines moves can affect how quickly branches are pruned. If a promising move is searched early, alpha may rise sooner at a Max node or beta may fall sooner at a Min node. This allows the agent to prune branches earlier. Minimax Alpha-beta pruning with move ordering supports policies that decide how possible moves are ordered.\\

In order to investigate what ordering works better, two distinct policies have been considered. Net score gain applies each possible move to a copy of the game and estimates the current player’s score gain as if the round ended immediately after that move. The moves are then ordered with the largest score gain first. Point based ordering instead assigns weights to features of the move. It favours completing or filling pattern lines and placing tiles in central wall columns, while penalising tiles sent to the floor or overflowing a pattern line. The moves are then ordered using the assigned weights. The graph below displays comparisons between the time taken to compute a single move at different depths across the two ordering policies, and no ordering shown as a baseline. It can be clearly seen that point based move ordering provides the best performance among the policies.

\subsubsection{Iterative Deepening}
Iterative deepening gives the agent a time limit for choosing each move. It searches first to depth one, then repeats the search at increasing depths, using alpha-beta pruning and the selected move-ordering policy. After each complete search, the agent keeps its chosen move. If the deadline is reached during a deeper search, that incomplete result is discarded and the move from the last completed depth is returned. The search can therefore reach different depths depending on the current game state. With a time limit of 5 seconds, iterative deepening is able to reach a depth of 4 initially and a depth of 6 later in the game once the possible number of moves reduce.


\subsection{Monte Carlo Tree Search}
Monte Carlo Tree Search (MCTS) is a simulation-based agent that estimates which move to choose by running simulations of possible games. Each node in its search tree records how often it has been visited and the reward accumulated from those simulations. Starting from the current position, the agent expands one untried legal move and simulates a game from the resulting game state using random moves until the game ends. It then passes the result back through the nodes visited in the tree. Once a node’s legal moves have been expanded, the Upper Confidence Bound applied to Trees (UCT) formula guides the selection of a child, balancing moves with promising results against moves that have received less attention. After the specified number of simulations, the agent returns the move corresponding with the most visited state from the start state.\\

Using tic-tac-toe and its starting state, the agent completed 1,000 simulations in 0.0174 seconds. Azul adds random factory refills during a game, which means MCTS needs to be adapted to explicitly handle random refills during the game.

\subsubsection{Azul Compatibility (Chance Handling)}
Azul’s random factory refills require the MCTS agent to distinguish a player’s move from a random event. When tree selection reaches the end of a round with a refill pending, it stops at that boundary. The simulation then samples one possible refill and continues playing to the end of the game. This allows for natural exploration of possible outcomes over many repeated game simulations. The graph below visualises a comparison between full game runtime and net score against a varying number of simulations. It can be seen that with an increase in the number of simulations, both the total game time as well as net score increase steadily. A single move computation for Azul with 1000 simulations takes roughly 0.957 seconds which is significantly faster than Minimax.

\subsubsection{Rollout Policy}
The chance-handling MCTS agent chooses between legal moves during simulations with equal chance. In Azul, some moves can place several tiles on the floor line, incurring penalties. During informal play-testing, the previous agent appeared to choose floor-line moves frequently. This motivated the use of rollout policies which favour certain moves over others during random simulations. The aim is to make simulated games more representative of plausible play, and hence arrive at better move predictions.\\

In order to investigate what rollout policy works better, two distinct policies have been considered. The point epsilon policy uses the point-based weights introduced for Minimax move ordering in Section 4.2.3, favouring pattern-line completion and central wall positions while penalising floor use and overflow. The score estimate policy approximates a move’s immediate scoring effect using projected wall points, pattern-line progress and floor penalties. At each simulation step, both policies select the highest ranking legal move while breaking ties randomly. With probability $\epsilon$, it instead selects a legal move at random, retaining randomness during simulations.\\

The graph below comparisons the two rollout policies against time taken for a full game and net score. The chance handling MCTS agent is also displayed as a baseline. Both policies perform significantly better than the previous MCTS baseline. Although point epsilon policy leads to stronger net scores at lower simulations, score estimation policy is stronger at higher number of simulations. This comes at a cost of additional computational time. However, this is acceptable since MCTS with the score estimation policy at 1000 simulations is able to compute a move in approximately 1.73 seconds.

\subsubsection{Tree Reuse}
The MCTS agent starts a new search tree whenever it chooses a move, discarding the visits and rewards collected during its previous computations during the same game. Tree reuse retains the subtree below the move it selected. On the agent’s next turn, it checks whether a child of that subtree matches the current game state. If one matches, that child becomes the new root and the agent adds further simulations to the information already recorded there. If none matches, it starts a new tree. This allows pre-existing computation to add onto and help the next set of simulations, potentially leading to better results due to a greater number of total simulations.
